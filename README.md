# 磁带灾备恢复演练（Flask · 读写流水线）

灾备值班员只有一台带机、两盘磁带，需要从带卷还原虚拟机镜像。本项目用本地文件
模拟磁带卷，提供一个 Flask 网页来选择带卷、填写**读带块数上限**、**暂存块数
上限**与可选的**每块写盘延迟**，并在额度内完成恢复演练；遇坏块或额度不足时报错，
且保留上一次成品。读带与写盘由两个线程流水线并行，缩短网页恢复时的读带等待。

## 磁带与恢复语义（按演练规则实现）

- 每套带卷最多两盘磁带、合计最多 12 个 **4 KiB** 镜像块；`manifest.json`
  记录每块的镜像块号、所在磁带、带上帧位置与 SHA-256，每块只出现一次。
- 磁带只能**从头顺读**。换带或回卷后，磁头回到第 0 帧；同一盘带在一次顺读
  会话内磁头自然前移，目标帧落后于磁头时才回卷。
- 顺读路径上**跳过的帧也算读带量**，回卷/换带后**重读的帧重复计数**。
- 提前读到、暂时不能按块号写出的块进入**暂存区**（内存/磁盘等价，本实现用
  内存承载，落盘镜像走临时文件），暂存块数峰值受暂存额度约束。
- 镜像只允许按块号 0、1、2…… **顺序追加**，不能回读、不能改已写块。
- 每个块在**入暂存前**（读带线程）与**写出前**（写盘线程）都核对 SHA-256；
  坏块立即失败。
- 任一额度不足或遇到坏块立即中止，删除半成品 `image.bin.part`，**上一次
  成品 `image.bin` 原样保留**；恢复期间仍可下载上次成品（原子发布）。

## 读带 / 写盘流水线（本次优化）

- **读带线程**独占磁带机械动作（挂带/换带/回卷/顺读）、读带延迟、入暂存前
  摘要核对与投递；**写盘线程**是唯一的写盘者，严格按块号顺序追加，承担写出前
  摘要核对与每块可配置的模拟写盘等待。
- 写盘等待期间读带继续推进，从而缩短网页恢复的读带等待；读带机械语义与计量
  规则完全不变，**同样的带卷与额度，成功恢复的实读块数不因优化增加**。
- 所有“前读后、等着追加”的已校验块都计入暂存；正在写盘中的那一块走唯一的
  直接交接槽，**不占暂存**。暂存满时若写盘者正忙，读带侧反压等待；写盘者
  一空出，**下一个应写的块仍可直接交接追加**，不会被暂存额度误杀。只有写盘者
  空闲却仍放不下时，才按原规则报暂存额度不足。
- 任一侧报错后，另一侧只允许做完**已经开始的读帧或写盘**即停；
  `simulate_recovery` 等两个线程都结束才返回，两侧停稳后才接下一单。
- 页面与接口新增指标 **与写盘重叠的读帧数**（读帧完成瞬间写盘仍在进行的帧
  计数），连同实读块数、暂存峰值一起在运行中实时轮询、结束后定稿。
- 写盘延迟沿用读带延迟的模拟方式：`WRITE_DELAY` 给每块默认等待秒数，
  页面表单可用 `块号:秒数`（逗号分隔，如 `0:1.5,3:0.2`）给指定块单独加延迟。

## 目录结构

```
app/
  storage.py   带卷发现、manifest 校验、定长帧顺读
  engine.py    读带/写盘流水线：磁头/换带/回卷、读带与暂存额度、双次摘要核对、
               只追加写、每块写盘延迟与重叠读帧计量
  web.py       Flask 应用、后台恢复线程、实时任务状态、成品下载
  templates/   单页界面（选带卷、填额度与写盘延迟、轮询实时指标、下载成品）
scripts/
  make_samples.py  生成三套样例带卷
tests/         引擎、流水线与 Web 自测（34 个用例）
run.py         本地开发入口
Dockerfile, docker-compose.yml
```

## 三套样例带卷（`scripts/make_samples.py` 生成）

| 带卷 | 布局 | 读带量 | 暂存峰值 | 换带 | 回卷 |
|---|---|---|---|---|---|
| `sample-ordered` | 块号沿顺读方向递增，块 0 在带头 | 12 | 0 | 1 | 0 |
| `sample-scrambled` | 每盘带块号沿顺读方向递减，未来块必须暂存 | 12 | 10 | 1 | 0 |
| `sample-bad` | 同乱序布局，块 11 带数据被故意损坏 | 失败 | — | — | — |

> 页面上每套带卷会显示“预估读带/暂存”，即贪心策略（提前读到的块全部暂存）
> 下的额度下限，与真实模拟同源计算。

## 本地运行

```bash
# 1) 安装依赖（无 pip/venv 的隔离环境可装到独立目录并用 PYTHONPATH 引用）
pip install -r requirements.txt

# 2) 生成样例带卷
python -I scripts/make_samples.py --root data/tapes

# 3) 启动（默认 0.0.0.0:8000）
python -I run.py
# 或 gunicorn（与容器一致，单 worker 多线程以保证任务状态语义）
python -m gunicorn --bind 0.0.0.0:8000 --workers 1 --threads 4 run:app
```

环境变量：`TAPE_ROOT`（带卷根目录，默认 `data/tapes`）、
`OUTPUT_ROOT`（成品目录，默认 `data/output`）、
`READ_DELAY`（每读一块的模拟延迟秒数，默认 `0.05`，设 0 最快）、
`WRITE_DELAY`（每块默认写盘延迟秒数，默认 `0`；页面可按块号覆盖）。

## Docker Compose

```bash
docker compose up --build
# 打开 http://localhost:8000
```

镜像内置三套样例带卷；带卷与成品分别挂载在命名卷 `tape-data`、`output-data`
（`/data/tapes`、`/data/output`）。

## 实现、验证与未完成项

### 已实现
- 读带线程 + 写盘线程流水线：写盘等待与读带并行，读带机械语义与计量规则不变，
  同带卷同额度实读块数与优化前完全一致。
- 有界暂存 + 直接交接槽：前读后等的块全计暂存，正在写的块不占暂存；暂存满且
  写盘忙时反压等待，写盘一空出下一个应写块直接交接，写盘空闲仍放不下才报
  暂存额度不足（乱序带在原额度 12 读 / 10 暂存下照常完成）。
- 每块可配置模拟写盘延迟（`WRITE_DELAY` + 表单 `块号:秒数`），读带延迟沿用。
- 入暂存前、写出前双次 SHA-256 核对；一侧失败后另一侧只做完已开始的读帧/写盘，
  `simulate_recovery` 等两侧停稳才返回；失败删半成品、保留上次成品并可下载，
  完整镜像按块号全部写盘成功后才经 `os.replace` 原子发布。
- 页面与 `/status` 实时展示实读块数、暂存峰值、与写盘重叠的读帧数。
- 带卷清单严格校验与完整磁带机械语义保持不变；Dockerfile + docker-compose
  （新增 `WRITE_DELAY`）支持容器启动。

### 已验证
- 34 个单元/集成测试全部通过（`python -I -m unittest`），连续 5 轮无竞态抖动。
- 题面场景实测（`sample-ordered`，暂存 1 块，块 0 写盘延迟 1.5 s，读带延迟
  0.03 s）：块 0 写盘未结束时块 1 已读完并通过 SHA-256 进入暂存；最终实读
  12 块、暂存峰值 1、重叠读帧 ≥1，成品 49152 字节逐块摘要全部一致。
- 墙钟对比（暂存 12、读带延迟 0.03 s）：无写盘延迟 0.37 s；块 0 延迟 1.5 s 时
  11 个读帧全部与写盘重叠，墙钟 1.58 s（串行需约 1.87 s）；每块延迟 0.3 s 时
  墙钟 3.79 s（串行需约 7.2 s）。
- 乱序带按原额度恢复成功：实读 12、暂存峰值 10、换带 1、回卷 0，与基线一致；
  坏带正确报块 11 且无成品，失败后上次成品仍可下载，停稳后下一单正常受理；
  非法写盘延迟配置与块号越界均返回 400。
- gunicorn 单 worker 多线程实际启动，`/`、`/status`、`/recover`、`/download`
  均正常，流水线指标与开发服务器一致。

### 未完成 / 限制
- 本环境无 docker 二进制，compose 配置仅做静态校验，未实际 `docker build`
  （容器入口已用同构的 gunicorn 命令在本机验证）。
- 恢复任务状态保存在单进程内存中（因此 gunicorn 固定单 worker）；多副本
  部署或进程重启后任务历史不保留（成品文件仍在）。
- 暂存实现为内存承载，未单独模拟“暂存写磁盘”的独立 IO 额度；按题意内存与
  磁盘暂存等价，统一计入暂存块数额度。
- 重叠读帧按“读帧完成瞬间写盘是否仍在进行”计数，是观测指标，不参与任何
  额度计量；暂存额度偏小时读带会被反压，重叠帧数相应减少，属预期行为。
